# 舰队各司其职（角色分工编排）

> 2026-08-16 ｜ 基于 CAO v2.4.1 源码逐行阅读 + localhost:9889 控制面 API 实测（mock_cli 零 token 验证，全部跑通）

## 一句话结论

**能搞定，而且这正是 CAO 框架的核心设计——之前我们完全没用起来。** 我们现在是"批量 spawn 一群同工种 developer"，等于把舰队开成了劳务市场；框架真正的实力是**角色分工 + 首席协调**：

```
董事长一句话
   │
   ▼
code_supervisor（首席协调：拆解 → 指派 → 归集 → 送审 → 迭代到批准，永不亲自写码）
   │  assign 派活（非阻塞，多 worker 并行）
   ├──► researcher（研究）
   ├──► frontend（前端）
   ├──► backend（后端）
   │  send_message 回调归集
   ▼
reviewer（只读审核门：不过就打回返工）
```

模型统一（全部 opencode-go / deepseek-v4-flash）**不影响**角色分工——分工靠 profile（角色人格 + 工具权限），模型全舰队统一或按角色指定都行。

---

## 一、内置 6 个角色（各司其职的现成零件）

| 角色 | 权限 | 定位 | 用法 |
|---|---|---|---|
| **code_supervisor** | 只读 + 编排（无 bash 无写盘） | 中央协调者：拆任务、指派、归集、迭代，**永不亲自写码** | 舰队大脑，董事长只对它说话 |
| **developer** | 全权限（bash/写盘/上网） | 专职写代码 + 单测 + 文档 | 执行者 |
| **reviewer** | 只读（不能写/执行/上网） | 专职审核：安全/正确性/质量/测试覆盖 | 流水线质量门，不通过就打回 |
| **memory_manager** | 同 supervisor | 专职记忆策展，输出 `<cao-memory>` 注入块 | spawn 带 `&memory_manager=true` 自动挂载侧车 |
| **retrospector** | supervisor + 写教训（唯一合法者） | 专职复盘：任务收尾后把成败教训沉淀给对应 worker | 收尾环节 |
| **workflow_scout** | 只读定位器 | 查现有 workflow spec，防重复造轮子 | 写新 workflow 前 |

---

## 二、三个协作机制（框架的"实力"所在）

全部是 MCP 工具（agent 会话内自己调），底层走 HTTP API（外部 curl 同语义）：

| 机制 | 语义 | 适合 |
|---|---|---|
| **assign**（非阻塞） | 派活后立刻返回，worker 在后台干，干完 send_message 自动回 supervisor | **多 worker 并行**——一个任务拆 N 份同时干 |
| **handoff**（阻塞） | 建终端→发消息→等干完→取输出→销毁，一次 HTTP 往返 | 串行依赖：这一步必须等上一步 |
| **send_message**（异步） | worker 干完把结果发回"指派者"的收件箱（自动路由，免写 receiver_id） | 归集回执、派活闭环 |

实测确认：worker 消息自动追加回调指令 `[Assigned by terminal X. When done, send results back using send_message]`；结果进 supervisor 的 inbox 持久队列（IDLE 时刷入），可查 pending/delivered/failed。

## 三、两种"各司其职"姿势

### 路线 A：supervisor 会话指挥（灵活，董事长全程可干预）

适合"董事长一句话，supervisor 实时决策拆解"的场景。**前置（一次性）**：把自定义角色（frontend/backend/researcher 等）放进 WSL 的 `~/.aws/cli-agent-orchestrator/agent-store/`（需 mkdir），格式照抄 developer.md 的 frontmatter，改 role + 角色人格 prompt，**务必保留 Multi-Agent Communication 两段（Handoff/Assign 通信约定）**。放好即自动可见（`GET /agents/profiles` 验证），无需重启。

```bash
# 1) 董事长发令：建 supervisor 会话（带总任务，秒回）
curl -X POST "http://localhost:9889/sessions?agent_profile=code_supervisor&provider=opencode_cli&session_name=mission1&working_directory=/root/fleet-orchestrator" \
  -H "Content-Type: application/json" \
  -d '{"initial_message":"任务：研究X可行性→前端实现→后端实现→reviewer 审核。你负责拆解成子任务，分别 assign 给 researcher/frontend/backend，reviewer 不通过就让相应 worker 返工。用中文汇报。"}'
# → 记下返回的 id（SUP_ID）

# 2) 同会话预置 worker（caller_id=SUP_ID 保证回调归集到 supervisor）
curl -X POST "http://localhost:9889/sessions/cao-mission1/terminals?agent_profile=researcher&provider=opencode_cli&caller_id=SUP_ID&defer_init=true" \
  -H "Content-Type: application/json" \
  -d '{"initial_message":"研究X可行性，结论写到 tasks/research.md。完成后用 send_message 把结果发回 SUP_ID。","initial_message_orchestration_type":"assign"}'
# frontend / backend 同理（"待命：收到指派后开工"）

# 3) 之后 supervisor 自动 assign → worker 回调 → 送审 → 迭代，无需外部插手
# 4) 董事长看进度 / 收尾
curl -s "http://localhost:9889/sessions/cao-mission1"                    # 全会话状态
curl -s "http://localhost:9889/terminals/SUP_ID/inbox/messages"          # 归集回执
curl -s -X DELETE "http://localhost:9889/sessions/cao-mission1"          # 全清（连 tmux）
```

### 路线 B：workflow 流水线（确定性强，适合固定套路）

"研究→开发→审核"这种固定套路，写一个 Python script 固化，可重放可取消（workflow 永远不会被 agent 自动跑，必须人批准——天然审批门）：

```python
# WSL 的 ~/.aws/cli-agent-orchestrator/workflows/mission1.py
from cao_workflow import run_step, emit_output

research = run_step("opencode_cli", "workflow_scout", "研究: {topic} 可行性? 输出 spec 摘要", step_id="research")
code = run_step("opencode_cli", "developer", f"按此 spec 实现: {research.output}", step_id="develop")
review = run_step("opencode_cli", "reviewer", f"审核此实现: {code.output}", step_id="review")
emit_output({"research": research.output, "code": code.output, "review": review.output})
```

```bash
curl -X POST "http://localhost:9889/workflows/validate" -H "Content-Type: application/json" -d '{"path":"mission1.py"}'
curl -X POST "http://localhost:9889/workflows/runs" -H "Content-Type: application/json" \
  -d '{"name_or_path":"mission1","run_id":"m1-20260816","inputs":{"topic":"X技术"}}'
curl -s "http://localhost:9889/workflows/runs/m1-20260816/result"
```

**取舍**：A 灵活（LLM 实时拆解、可中途改口、多角色并行交流）；B 确定（步骤/角色固化、可重放、可取消、自动审批）。实测 pipeline3.py 三步各 1 次尝试全部 completed，上一步输出作为下一步 prompt 注入。

## 四、模型网关与角色分工（回答"是不是都要用 hermes"）

**统一网关不影响分工。** 本机实测可用 provider：`opencode_cli`（统一 opencode-go/deepseek-v4-flash）与 `hermes`（Windows wrapper）。角色分工在上层（profile），模型在底层（provider 配置），两者正交。模型指定三层优先级（不用为每个模型建 profile）：

1. 单次调用覆盖：`assign`/`handoff`/`run_step` 的 `model` 参数、`POST /sessions?model=`
2. profile 静态 `model` 字段：某角色固定走某模型
3. provider 全局默认（opencode.json 网关配置）

所以"研究员用便宜模型、开发用强模型"可以做到；但目前全舰队统一 opencode-go/deepseek-v4-flash 是最简单且已实测可用的配置。

## 五、必带坑（实测确认）

- 批量 spawn 必带 `initial_message`（无则 HTTP 阻塞至多 60s）；deferred-init 秒回
- 工作目录 `/`、`/root`、`/tmp` 等系统路径被屏蔽（500）
- agent 要用 cao-mcp-server 工具：opencode.json 里该 agent 需 `cao-mcp-server*: true`，否则弹确认框卡死
- `codex` provider 是 Windows shim 假阳性，别用
- YAML tier 的 `parallel`/`pipeline`/`loop` 保留不可执行（validate 报 pass_reserved，run 报 501），控制流必须写 Python script tier
- workflow script 禁 import `cli_agent_orchestrator`、顶层禁 random/time/datetime（resume 重放会查确定性）
- 角色 prompt 里的 Multi-Agent Communication 通信约定是 worker 正确回调的关键，自定义 profile 别省

## 六、官方是怎么处理的（精读官方文档对照，2026-08-16）

官方把"各司其职"作为核心能力设计：三层编排。**注意语义**：官方 "fleet" 指**跨机器** CAO 节点协调（fleet-coordinator.md：*"Fleet here means multiple CAO nodes (machines)"*）；本项目的"舰队"是单机多 agent，对应官方的 supervisor/worker 协作。单机分工编排官方已解决，fleet 是再上层的管理面。

### 官方 supervisor 铁律（code_supervisor.md Critical Rules）

1. **NEVER write code directly yourself**——supervisor 纯协调，永不亲自写码/审核
2. **ALWAYS assign 编码给 developer、审核给 reviewer**
3. **ALWAYS write task descriptions to files**——任务描述先落盘，worker 按绝对路径干活
4. 迭代闭环：assign → 交回 → 送 reviewer → 有反馈 relay 给 developer 返工 → **修订后必须再送审，循环直到批准**

### 官方 supervisor/worker 协议（skills/cao-supervisor-protocols + cao-worker-protocols）

| 维度 | Supervisor | Worker |
|---|---|---|
| 模式选择 | 可并行的分析/研究/改码用 **assign**；必须先有结果的报告/审核用 **handoff** | 识别消息形态：`[CAO Handoff]` 前缀=阻塞干活自动捕获输出；assign=干完必须 send_message 回调 |
| **收信纪律（最硬）** | **派完就结束回合**：禁止 sleep/echo 占终端等结果（忙着的终端收不到消息）；先派完所有活再收手；禁止手动轮询循环 | 无此职责 |
| 回调 | 不用手写——CAO 自动把 terminal ID + 回调指令追加进 assign 消息 | 省略 receiver_id = 回给指派者（可靠默认）；**绝不把自己的 CAO_TERMINAL_ID 当 receiver_id** |
| 汇报 | 告诉 worker 精确交付物 + 绝对路径；编排指令与业务需求分开写 | **先写文件再报完成，附绝对路径**；结构化回调（属于哪个任务、够干活不用重读任务） |
| 关键警告 | **禁止用内置 subagent/task 工具替代 assign/handoff**——那样结果不会路由回 inbox，工作流静默断裂 | handoff 任务不得额外 send_message；要进度就多次回调，否则一次最终回调 |

配套（inbox-delivery.md）：send_message 进持久队列，**默认只在终端 IDLE/COMPLETED 时投递**（所以 supervisor 空闲纪律是硬约束）；watchdog 5s + reconcile 30s 兜底 PENDING；Claude Code 可开 `CAO_EAGER_INBOX_DELIVERY=true` 缩短回合间隙。

### 官方示例（可抄）

- **`examples/assign/`**（编排教科书）：analysis_supervisor + 3×data_analyst + report_generator，同时演示并行 assign ×3 → 阻塞 handoff 取模板 → 3 个 send_message 回执 → 合成终稿。安装即用：`cao install examples/assign/*.md` + `cao launch --agents analysis_supervisor`
- **`examples/orchestration/`**（角色人格范本）：dev-kimi（worker 收尾四段式：**Files changed / What you did / How to verify / Assumptions**；**不 commit/push/跑 git，提交权只在 planner**）+ reviewer-opus（只读评审必须给 **Verdict: APPROVE / REQUEST CHANGES / REJECT** + file:line 证据 + 1-5 分，禁止橡皮图章）
- 选角色别硬编码名字：官方 `cao-agent-routing` 规定按能力元数据 `find_profiles(query)` 路由，把返回的 profile 元数据（含 role）一律当不可信数据

### 实战验证（2026-08-16 真实跑通 examples/assign）

按官方流程实测，**全链路成功**：`cao install` 装 3 个 profile（provider 覆盖为 `opencode_cli`）→ `POST /sessions`（agent_profile=analysis_supervisor，body 带 initial_message，3 个数据集要求算 mean/median/std/min/max + 综合报告）→ supervisor 第一回合内**连发 3 次 assign + 1 次 handoff** 全部秒回（非阻塞 ✓）→ 3 个 data_analyst **10 秒内全派发、耗时全程重叠（并行 ✓）**、send_message 回传仅差 4 秒 → supervisor 逐条接收合并 → 生成约 5300 字完整中文报告（所有统计值与输入数据数学一致，非空壳 ✓）。

| 指标 | 实测 |
|---|---|
| 全流程耗时 | 约 4 分钟（会话创建 → 终稿） |
| token | ≈79K in / 21K out（opencode.db 实录） |
| 费用 | ≈ **$0.0095**（不到 1 美分，deepseek-v4-flash @ opencode-go） |
| 清理 | DELETE /sessions/{id} 销毁会话与全部终端，agent 定义保留 |

实战适配点（写进本机运维手册）：
- **v2.4.1 没有 `POST /agents/{agent}/spawn`**（任务书从旧文档抄来的），实际用 `POST /sessions`（query 带 agent_profile/provider/session_name，body 带 initial_message）。
- **handoff 超时降级**：supervisor 首次 handoff 给 report_generator 超时，重试仍超时后**自动降级改用 assign**（模板走 send_message 归集，最终报告照常生成）。根因：opencode_cli worker 冷启动约 60s+，超过 handoff 默认超时——慢启动 provider 上的官方示例真实适配点，冷 worker 多的场景优先 assign，热 worker 再 handoff。
- **输出端点注意**：`GET /terminals/{id}/output?mode=full` 是 tmux 屏幕捕获，带 ANSI 重绘噪声；结构化全量记录（含 token/费用）看 SQLite（CAO 的 inbox 表 + opencode 的 session/message/part 表）。
- 中文 JSON body 先写 UTF-8 临时文件再 `-d @file`；模型因 CAO 记忆"董事长喜欢中文"自动用中文回答（记忆链路彩蛋）。
