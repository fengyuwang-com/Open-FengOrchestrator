## 一、原则原文与判定标准

董事长原话（2026-09-13）：

> AI 时代的我们不能拘泥于以前那种——跟一个客户端交互，交互完了把所有结果都留在客户端。应该是**资料留在本地**，交互的结果当然我可以帮他备份。通过 Skill 的方法和看 Web UI 的方法跟 AI 交互——**有 UI，但实际上我只需要跟 AI 说话就行**，大部分工作无非就是文字交流。UI 只是为了让不懂的人懂一下，或者让他们看的时候方便一点。我们所有东西就是两个层次：一个是跟 AI 对话，一个是给人看的。Web UI 里面要有 Skill，那个 Skill 就是给客户用的。

形式化为**两层界面原则（2LIP）**：

| 层 | 服务对象 | 形态 | 职责 | 反模式 |
|---|---|---|---|---|
| **对话层（L1）** | 操作者 | 自然语言 + Skill | 承载全部日常操作 | 把操作埋进按钮让 AI 够不着 |
| **观景层（L2）** | 观看者（不操作） | 只读 Web UI / 仪表盘 | 展示状态与结果，供理解/验收/演示 | 在观景层开发写操作 |

资源约束：**C1 资料本地**（真理源恒为本地文件/库，客户端只持有副本或视图）；**C2 结果可备份**（产出落入 git 双推 / FlyGo 多副本管道）。

**符合性四问**（审计用）：① 数据在不在本地？② 日常操作走不走对话？③ UI 是否只读？④ 产出能否备份？

### 历史脉络（与本原则相关的既往决策）

- 2026-09-12 01:30（FENGMEM 第 N 轮）：董事长要求"给舰队做个 GUI，让老登一眼看懂谁在干活谁在摸鱼"→ 落地为 CAO 官方 Web UI（localhost:9889，web/ npm build 产物入 site-packages，tmux 托管 cao-server）。这是本原则 L2 层的舰队实现。

## 二、全生态审查明细（2026-09-13 实测）

### 2.1 FengInvest —— ✅ 标杆，不动

- **UI**：`fengweb/`（TS/Express/EJS，端口 23456），研究报告浏览器，只读渲染 md。
- **四问**：① 2.7GB market_data.db + holdings/portfolio/reviews 全部本地 gitignored ✅ ② 62 个工具全由 AI 调用，无 UI 操作 ✅ ③ fengweb 纯只读 ✅ ④ git 双推 + changesets 增量 ✅
- **结论**：2LIP 教科书实现，作为全生态标杆，零改动。

### 2.2 FengMedia —— ⚠️ 一处偏差，微调

- **UI**：`webui/`（Express+EJS+TS，端口 23457，复用 fengweb 栈），作战地图/选题库/打卡。
- **四问**：① 数据全在本地 md/json（content/topics.json 等）✅ ② 日常操作走对话（/publish、/rage-mode 等 skill）✅ ③ **选题库增删、打卡勾选是写操作混进了 UI** ⚠️ ④ git 可备份 ✅
- **结论**：README 本就自定"UI 只做可视化+轻交互"，执行走了样。改造：写操作收进对话（"记一个选题 X"→ AI 落 topics.json；"打卡"→ 落 checkin.json），webui 砍掉 POST 路由只留展示。
- **改造量**：小（三条路由去写操作 + 一条 Skill 约定）。

### 2.3 FlyGo —— ➖ 特殊：UI 是产品本体，缺客户对话层

- **UI**：panel（Rust/axum，8388，托盘托管）+ control-plane admin UI（9001）+ webcli（8443）+ APK。
- **判定**：FlyGo 是对外商业产品，"1 EXE + 1 APK"是产品哲学，UI 是交付物本身，**不适用"L2 退居"条款**。但按董事长"Web UI 里要有给客户用的 Skill"要求，**缺的是对话层**：客户目前只能点按钮，售后诊断/配对/换新/答疑应可"跟客服 AI 说话"。
- **结论**：借 OpenAI Apps SDK 的 MCP-UI 模式——**Skill 是主体，UI 是 Skill 返回的可视化附件**，在产品内嵌对话入口，面板按钮退居展示与兜底。不破坏"1 EXE+1 APK"（对话入口是面板里的一个组件，不是新门户）。
- **时机**：随商业上线（T-11/T-12 之后），不阻塞本地开发。

### 2.4 FengOS —— ✅ 生态观景台本体，升级为统一入口

- **UI**：3D 星系渲染 FengProj 全部项目 + 实时系统探针，uvicorn :8765，计划任务开机自启，防火墙放行供 Tailscale 访问。
- **判定**：这就是"观看台"的雏形，方向完全正确。缺口：只管目录与系统探针，未接入各系统业务视图。
- **改造**：升级为**统一观景入口**——聚合 FengInvest 报告（23456）/FengMedia 作战地图（23457）/CAO 舰队状态（9889）/FlyGo 面板状态（8388）的只读视图。
- **铁律**：**iframe/链接聚合，不搬数据**——各系统保持自己的端口与真理源，FengOS 只做导航+状态探针。守住 C1 单一真理源，避免再造一套需要同步的副本。
- **Generative UI 提示**：观景页不必精装修，可做"AI 按需生成页面"（临时看细节用生成视图，日常扫一眼用固定视图），省维护成本。

### 2.5 CAO Web UI（9889）+ webcli（8443/8788）—— ✅ 符合

- CAO Web UI = "看子代理在干嘛"的 L2 实现；webcli = 对话层通道（浏览器真终端），非观景台。均符合，不动。

### 2.6 纯工具（TTS-UI、Speed-Change）—— ➖ 不适用

- 桌面 GUI 一键工具，发给外部用户的成品，UI 即交互本体，无 AI 层需求。2LIP 不适用，零改动。

### 2.7 外来件（tickflow-stock-panel、MoneyPrinterTurbo 等）

- 别人的开源项目自托管，不在审查范围。

## 三、业界对位（2026-09 联网检索，证明非孤例）

1. **Chat is the interface**：YC 的 Gary Tan / Jared Friedman 公开推翻早前立场，确认"对话即界面"（Pete Koomen 访谈，biggo.com）；产品侧 neww.ai（"Chat is the interface. The operating system is the product."）、arg.ai（无 SaaS UI，Agent 经聊天读写文件）、XBuild（对话即估算流程）。
2. **Generative UI**：Google Cloud 定义"UI 由 AI 按需拼装而非开发者写死"；Thesys/Open Data Science 论证仪表盘→生成式界面演化（"界面变成一次回应，而不是一个目的地"）；r/UXDesign 反思：固定仪表盘在可扫视性上不可替代 → 合成 2LIP 立场：观景层保留但不精装修。
3. **MCP Apps / OpenAI Apps SDK**：MCP server（给客户用的 Skill）返回 UI 资源，聊天流内 React 组件渲染（Zillow 房源卡）→ FlyGo 客户对话层的官方参照形态。
4. **Local-first AI Agent**：fast.io（Agent 本地读写优先+异步同步备份）、r3zz.io（个人 Agent 本地全栈：运行时/记忆/技能/定时任务）、Medium 分层策略（数据去向由敏感性决定）→ C1/C2 的业界共识：完全离线不现实，关键是数据分级。

## 四、三元界面命题（与文档操控 AI 的合流）

2LIP 回答"人怎么操作 AI"；"AI 怎么被操作"由**文档**回答——FengASNI DocsParadigm（70 份治理文档共性分析）已收敛出四件套范式：AGENTS.md（规则唯一真源）/ MISSION.md（北极星+DoD）/ todo.md（账本）/ FENGMEM.md（日志），Skill（SKILL.md）为可复用操作封装。AI 开工先读文档、行动结果回写账本、规则变更回写 AGENTS——**文档即控制平面**。

由此，AI 时代软件交互是三元结构：

```
人 ──自然语言──> AI ──工具调用──> 系统
│                                ↑
└──文档（规则/目标/账本/日志）──────┘
   对话层=人操作AI ｜ 文档层=治理AI与系统 ｜ 观景层=人确认状态
```

文档层约束对话层（Skill 必须符合 AGENTS 铁律），对话层驱动系统，观景层只反映产出。这解释了 2LIP 系统为何不需要复杂权限后台——治理由文档层承担。
